## 1. Назначение и источники

Документ задаёт порядок разработки первой версии WirePack. Подробная разбивка задач находится в `docs/development-plan-detailed.md`.

Источники:

- `docs/requirements.md` — требования к продукту.
- `docs/architecture.md` — архитектура и зависимости.
- `docs/optimization.md` — требования к алгоритму оптимизации.
- `docs/geometry.md` — математическая модель геометрии.
- `docs/data-format.md` — структура данных и формат проекта.
- `AGENTS.md` — правила работы с проектом.
- `Directory.Build.props` — общие настройки сборки.

План не вводит новых требований. Утверждения, которых нет в перечисленных источниках, помечены как предложения и требуют согласования.

 Ссылка на чек-лист выполнения: `docs/development-plan-checklist.md`

## 2. Архитектура

| Проект | Ответственность | Ссылки |
|--------|-----------------|--------|
| `WirePack.Core` | Геометрическое ядро, предметные модели, DTO проекта, MEC, независимая проверка | `docs/architecture.md:34-48` |
| `WirePack.Optimization` | Поиск компактных укладок, перезапуски, остановка, бюджет времени | `docs/architecture.md:50-66` |
| `WirePack.App` | Avalonia UI, MVVM, визуализация, JSON-сохранение и открытие | `docs/architecture.md:18-32` |
| `WirePack.Export` | Зарезервирован, в первой версии не реализуется | `docs/architecture.md:68-72` |

Допустимые зависимости:

```text
WirePack.App → WirePack.Core
WirePack.App → WirePack.Optimization
WirePack.Optimization → WirePack.Core
WirePack.Export → WirePack.Core
```

Ссылки: `docs/architecture.md:174-185`.

Ограничения:

- `WirePack.Core` не зависит от UI и остальных проектов (`docs/architecture.md:48`, `docs/architecture.md:183`).
- `WirePack.App` не ссылается на `WirePack.Export` в первой версии (`docs/architecture.md:185`).
- UI не реализует геометрические вычисления (`docs/architecture.md:189-192`).
- Модель данных проекта не размещается в `WirePack.App` (`docs/architecture.md:193`).

## 3. Базовые требования

- Поддерживаются наборы до **100 проводов** (`docs/requirements.md:33`).
- Расчёт ограничен **60 секундами** с момента запуска оптимизации (`docs/requirements.md:82-83`).
- При остановке по таймауту или по запросу пользователя сохраняются лучшие найденные варианты (`docs/requirements.md:80-83`).
- Находится **до пяти** геометрически различных вариантов (`docs/requirements.md:59`).
- Если пять вариантов не найдены, расчёт продолжается до 60 секунд или ручной остановки (`docs/optimization.md:56`, `docs/optimization.md:117`).
- Раннее завершение возможно при достижении критерия достаточности (`docs/requirements.md:84`, `docs/optimization.md:121-126`).
- Результат не выдаётся за доказанный глобальный оптимум (`docs/requirements.md:61`, `docs/optimization.md:23`).
- Параметры алгоритма пользователь не настраивает (`docs/requirements.md:95-97`).
- Результат воспроизводим при одинаковых входных данных, кроме срабатывания аварийного таймаута (`docs/requirements.md:85`, `docs/optimization.md:130-134`).
- Поддерживаются Ubuntu и Windows (`docs/requirements.md:99-102`).
- Проект сохраняется и открывается в JSON с проверкой версии и данных (`docs/requirements.md:89-91`, `docs/data-format.md:51-68`).

## 4. Алгоритм оптимизации

Основной алгоритм первой версии — **сжатие пучка с квазистатической релаксацией** (`docs/optimization.md:70-76`). Алгоритм эвристический (`docs/optimization.md:72`).

Шаги:

1. Построить начальную допустимую укладку (`docs/optimization.md:80`).
2. Вычислить MEC: центр `c` и радиус `R` (`docs/optimization.md:81`).
3. Перевести укладку так, чтобы центр MEC находился в начале координат (`docs/optimization.md:82`).
4. Уменьшить целевой радиус: `R_target = R - delta` (`docs/optimization.md:83`).
5. Выполнить квазистатическую релаксацию при неподвижном центре (`docs/optimization.md:84`).
6. Если укладка допустима — пересчитать MEC, перецентрировать, обновить лучший результат и продолжить сжатие (`docs/optimization.md:85-89`).
7. Если допустимую укладку получить не удалось — уменьшить шаг `delta` или выполнить перезапуск (`docs/optimization.md:90-91`).
8. Повторять до выполнения критерия остановки (`docs/optimization.md:92`).

Критерий раннего завершения:

- найдено целевое количество различных вариантов (до пяти);
- в течение `N` последовательных итераций лучший диаметр не улучшается больше `eps`.

Ссылки: `docs/optimization.md:121-126`. Улучшением считается уменьшение диаметра больше `eps` (`docs/optimization.md:126`). Значение `N` подбирается на бенчмарках (`docs/optimization.md:57`, `docs/optimization.md:126`).

Детерминированность:

- по умолчанию используется фиксированный seed (`docs/optimization.md:130`);
- последовательность начальных укладок и перезапусков детерминирована (`docs/optimization.md:131`);
- критерий отсутствия улучшений измеряется в итерациях, а не в секундах (`docs/optimization.md:132`);
- при срабатывании аварийного таймаута строгая воспроизводимость не гарантируется (`docs/optimization.md:134`).

## 5. Геометрическое ядро

Основные сущности: точка, окружность, провод, компоновка проводов (`docs/architecture.md:90-94`, `docs/geometry.md:19-37`).

Операции:

- расстояние между точками;
- проверка пересечения окружностей;
- проверка касания, касание допустимо;
- проверка нахождения окружности внутри другой окружности;
- определение MEC для набора проводов.

Ссылки: `docs/architecture.md:96-101`, `docs/geometry.md:41-59`.

MEC для проводов разных радиусов — взвешенная MEC:

```text
R = min_c max_i (|p_i - c| + r_i)
```

Ссылки: `docs/architecture.md:103-105`, `docs/geometry.md:76-86`. Это не MEC центров с добавлением максимального радиуса (`docs/geometry.md:84`). Центр MEC не является независимой переменной (`docs/geometry.md:86`).

Для численных проверок используется `double` и согласованный допуск (`docs/requirements.md:47-52`, `docs/geometry.md:109-113`).

Конкретный вычислительный алгоритм MEC выбирается при реализации и проверяется тестами на точность и скорость (`docs/geometry.md:90`). Предлагается отдельный research spike: сравнить точный/рандомизированный и численный варианты, замерить точность и производительность. Это предложение, а не утверждённое требование.

## 6. Модель данных и сохранение

- DTO проекта размещаются в `WirePack.Core` в отдельном пространстве имён и не используют типы геометрического ядра (`docs/architecture.md:142`).
- JSON-сериализация выполняется в `WirePack.App` (`docs/architecture.md:142`).
- Проект содержит версию формата, исходные группы проводов и результаты расчёта (`docs/data-format.md:16-20`).
- Каждый вариант содержит идентификатор, внутренний диаметр трубки, центр трубки, координаты центров проводов и их диаметры (`docs/data-format.md:35-41`).
- При открытии проверяются обязательные поля, диаметры, количество, координаты, размеры и соответствие результатов исходному набору (`docs/data-format.md:59-66`).
- Сохранённые центр и диаметр пересчитываются по координатам и проверяются (`docs/data-format.md:47`).
- При изменении исходных данных сохранённые результаты считаются устаревшими (`docs/data-format.md:68`).

## 8. Критерии готовности

- Сборка без предупреждений; `TreatWarningsAsErrors` уже включён (`Directory.Build.props:7`).
- Все автотесты проходят (`docs/architecture.md:158`, `AGENTS.md:67-71`).
- Для 100 проводов расчёт завершается не позднее 60 секунд (`docs/requirements.md:118`).
- Ранняя остановка работает по критерию `N` итераций без улучшения (`docs/optimization.md:121-126`).
- При остановке и таймауте лучшие результаты сохраняются (`docs/requirements.md:80-83`, `docs/optimization.md:49-53`).
- Результат воспроизводим при фиксированном seed, кроме таймаута (`docs/requirements.md:85`, `docs/optimization.md:130-134`).
- Все возвращённые решения проходят независимую проверку через Core (`docs/optimization.md:177`).
- Сохранение и открытие проекта работают с проверкой версии и данных (`docs/data-format.md:51-68`).
- Приложение работает в Ubuntu и Windows (`docs/requirements.md:99-102`, `docs/requirements.md:117`).
