# WirePack — архитектура приложения

**Версия:** 0.1  
**Статус:** Черновик

## 1. Общая архитектура

WirePack разрабатывается как настольное приложение на C# с использованием .NET 10 и Avalonia UI.

Архитектура должна разделять пользовательский интерфейс, геометрические вычисления и алгоритмы оптимизации.

Геометрическое ядро и алгоритмы оптимизации не должны зависеть от пользовательского интерфейса и конкретной операционной системы.

## 2. Структура решения

Решение состоит из следующих проектов:

### 2.1. WirePack.App

Пользовательский интерфейс приложения.

Ответственность:
- Ввод исходных данных.
- Запуск и остановка расчёта.
- Отображение найденных вариантов.
- Графическая визуализация компоновки проводов.
- Сохранение и открытие проектов в JSON с использованием модели данных проекта из WirePack.Core.
- Отображение ошибок и состояния расчёта.

Технологии:
- Avalonia UI.
- MVVM.

### 2.2. WirePack.Core

Геометрическое ядро и основные предметные модели.

Ответственность:
- Представление проводов и их геометрических параметров.
- Представление геометрического расположения проводов.
- Геометрические операции.
- Проверка пересечений проводов.
- Проверка размещения проводов внутри окружности.
- Определение минимальной охватывающей окружности для заданного расположения проводов.
- Модель данных проекта (DTO), не зависящая от внутренней реализации геометрии и UI.
- Независимая проверка корректности найденных решений.

Проект не должен зависеть от Avalonia UI и других компонентов пользовательского интерфейса.

### 2.3. WirePack.Optimization

Поиск оптимального расположения проводов.

Ответственность:
- Формирование начальных вариантов размещения.
- Поиск компактных вариантов компоновки.
- Использование геометрического ядра для проверки решений.
- Поиск нескольких различных вариантов.
- Сохранение лучших найденных решений в процессе расчёта.
- Поддержка остановки расчёта.
- Соблюдение бюджета времени 60 секунд и автоматическая остановка по таймауту.
- Выдача лучших найденных результатов в любой момент расчёта.
- Воспроизводимость результатов при фиксированном seed.
- Передача найденных решений вызывающему компоненту.

Проект зависит от WirePack.Core.

### 2.4. WirePack.Export

Вспомогательные операции экспорта.

Проект зарезервирован для возможного расширения в будущем. В первой версии не реализуется, поскольку экспорт не входит в требования первой версии. WirePack.App не ссылается на этот проект до начала его реализации.

## 3. Взаимодействие компонентов

Общий поток работы:

1. Пользователь вводит группы проводов в WirePack.App.
2. Приложение преобразует введённые данные в модель расчёта.
3. WirePack.Optimization получает исходные данные и запускает поиск.
4. Оптимизатор использует WirePack.Core для геометрических вычислений и проверки расположения.
5. Найденные решения передаются в WirePack.App.
6. Интерфейс отображает результаты пользователю.
7. При необходимости пользователь сохраняет проект.

## 4. Геометрическое ядро

Геометрическое ядро должно быть самостоятельным и не зависеть от UI.

Основные геометрические сущности:
- Точка на плоскости.
- Окружность.
- Провод с заданным наружным диаметром.
- Геометрическая компоновка проводов.

Геометрические операции:
- Расчёт расстояния между точками.
- Проверка пересечения окружностей.
- Проверка касания окружностей (касание считается допустимым).
- Проверка нахождения окружности внутри другой окружности.
- Определение минимальной охватывающей окружности (MEC) для набора проводов.

MEC (Minimum Enclosing Circle) для набора проводов — окружность с центром `c` и минимальным радиусом `R`, для которой выполняется условие `|p_i - c| + r_i <= R` для каждого провода. Радиус вычисляется как `R = min_c max_i (|p_i - c| + r_i)`, где `p_i` — центр провода, `r_i` — его радиус.

Для проводов разных радиусов используется взвешенная MEC кругов. Это не MEC центров с добавлением максимального радиуса. Центр MEC не является независимой переменной: для заданной укладки он определяется по координатам проводов. В типичном случае окружность определяется двумя или тремя опорными проводами, касающимися её границы.

Все вычисления выполняются в миллиметрах с использованием `double` и согласованного численного допуска.

## 5. Оптимизация

Алгоритм оптимизации должен быть отделён от геометрического ядра.

Его задача — найти допустимое расположение всех заданных проводов с наименьшим найденным диаметром охватывающей окружности.

Основной алгоритм первой версии — сжатие пучка с квазистатической релаксацией. Алгоритм должен:
- Находить начальные допустимые компоновки.
- Улучшать найденные компоновки.
- Искать несколько геометрически различных решений.
- Передавать лучшие решения по мере их обнаружения.
- Корректно реагировать на запрос остановки.
- Укладываться в бюджет 60 секунд для наборов до 100 проводов.
- Завершаться раньше 60 секунд при достижении критерия достаточности.
- Быть воспроизводимым при фиксированном seed. Исключение — срабатывание аварийного таймаута.
- Не считать найденное решение доказанным глобальным оптимумом без математического подтверждения.

Алгоритм является эвристическим. Конкретные параметры и критерий раннего завершения определяются в `optimization.md` и подбираются на бенчмарках. Архитектура допускает замену или добавление алгоритма оптимизации без изменения геометрического ядра.

## 6. Модели данных и сохранение проектов

Для хранения проекта используется отдельная модель данных, не зависящая от внутренней реализации геометрического ядра и UI.

Проект должен содержать:
- Версию формата проекта.
- Исходные группы проводов.
- Найденные варианты компоновки.
- Координаты центров проводов.
- Центр и рассчитанный диаметр охватывающей окружности.
- Уникальные идентификаторы вариантов.

Формат хранения — JSON.

Модель данных проекта размещается в WirePack.Core в отдельном пространстве имён и не использует типы геометрического ядра. JSON-сериализация выполняется в WirePack.App.

## 7. Визуализация

Визуализация выполняется средствами Avalonia UI.

Отображение компоновки должно:
- Показывать границу защитной трубки.
- Показывать каждый провод в виде окружности.
- Сохранять пропорции геометрических объектов.
- Обеспечивать масштабирование изображения для удобного просмотра.

Геометрические координаты не должны зависеть от масштаба отображения.

## 8. Тестирование

Геометрическое ядро и алгоритмы оптимизации должны иметь автоматические тесты. Для автотестов используется xUnit. Тестовые проекты `tests/WirePack.Core.Tests` и `tests/WirePack.Optimization.Tests` должны включаться в решение.

Основные направления тестирования:
- Корректность геометрических операций.
- Проверка пересечений и касаний.
- Проверка нахождения проводов внутри трубки.
- Корректность определения минимальной охватывающей окружности.
- Корректность результатов оптимизации.
- Корректность сохранения и открытия проектов.
- Производительность на наборах до 100 проводов.
- Соблюдение 60-секундного таймаута.
- Корректность раннего завершения по критерию достаточности.
- Воспроизводимость результатов при фиксированном seed.

Найденные оптимизатором решения должны дополнительно проходить независимую геометрическую проверку.

## 9. Зависимости между проектами

Допустимые зависимости:

- WirePack.App → WirePack.Core
- WirePack.App → WirePack.Optimization
- WirePack.Optimization → WirePack.Core
- WirePack.Export → WirePack.Core

WirePack.Core не зависит от остальных проектов.

WirePack.App не ссылается на WirePack.Export в первой версии.

## 10. Основные архитектурные ограничения

- Геометрическое ядро не зависит от UI.
- Алгоритмы оптимизации не содержат кода визуализации.
- UI не реализует геометрические вычисления.
- Все геометрические проверки выполняются через WirePack.Core.
- Модель данных проекта не размещается в WirePack.App.
- Основной алгоритм первой версии — сжатие пучка; допускается его замена по результатам бенчмарков.
- Архитектура должна допускать замену или добавление алгоритмов оптимизации без изменения геометрического ядра.
