# Инструкция по выпуску релизов WirePack

В данном документе описан процесс сборки, тестирования и публикации релизов проекта **WirePack** с использованием GitHub Actions и Git-тегов.

## 1. Принцип работы релизов

Процесс выпуска релизов полностью автоматизирован через GitHub Actions (`.github/workflows/release.yml`). 
- **Важно:** обычные коммиты и отправка (`push`) изменений в ветку `main` **не создают** релизы и не запускают процесс публикации.
- Релиз создается **исключительно** при отправке в удаленный репозиторий Git-тега, начинающегося с буквы `v` (например, `v0.2.0`, `v0.2.1`).
- При поступлении тега GitHub Actions автоматически выполняет сборку решения, запускает тесты, формирует автономные (self-contained) пакеты для Linux x64 и Windows x64, упаковывает их в ZIP-архивы и создает официальный GitHub Release с автоматически сгенерированными заметками о выпуске (Release Notes).

## 2. Правила выбора номера версии

Проект использует семантическое версионирование (`MAJOR.MINOR.PATCH`). 
- Текущая версия приложения в проекте — **`0.2.0`**.
- **MINOR** (вторая цифра) увеличивается при добавлении значительной функциональности при сохранении обратной совместимости (например, переход от `0.2.0` к `0.3.0`).
- **PATCH** (третья цифра) увеличивается при исправлении ошибок и мелких доработках (например, выпуск исправления `v0.2.1` после `v0.2.0`).

### Примеры версий:
- Первый выпуск: тег **`v0.2.0`** (соответствует текущему состоянию версии `0.2.0`).
- Следующий выпуск (например, исправление или небольшое обновление): тег **`v0.2.1`**.

## 3. Подготовка к выпуску

Перед созданием тега убедитесь, что:
1. Все изменения зафиксированы в ветке `main` и прошли локальное тестирование.
2. Локально успешно выполняются тесты и сборка проекта:
   ```bash
   dotnet test -c Release
   ```
3. Версия в `Directory.Build.props` соответствует выпускаемой версии (например, `<Version>0.2.0</Version>`). *Примечание: если выпускается версия `0.2.1`, предварительно обновите версию в `Directory.Build.props`, зафиксируйте изменения в `main` и только после этого ставьте тег.*

## 4. Создание и отправка тега

Создание тега выполняется в локальном репозитории с последующей отправкой на GitHub.

### Пример первого выпуска (`v0.2.0`):
```bash
git tag v0.2.0
git push origin v0.2.0
```

### Пример последующего выпуска (`v0.2.1`):
```bash
git tag v0.2.1
git push origin v0.2.1
```

## 5. Проверка выполнения GitHub Actions

1. Перейдите на страницу вашего репозитория на GitHub во вкладку **Actions**.
2. Вы увидите запущенный workflow **Release** для отправленного тега.
3. Workflow выполняет следующие этапы:
   - `test` — запуск всех автоматических тестов (`WirePack.Core.Tests`, `WirePack.Optimization.Tests`, `WirePack.App.Tests`).
   - `build` — сборка и публикация self-contained версий для `linux-x64` и `win-x64`, а также упаковка в `WirePack-linux-x64.zip` и `WirePack-win-x64.zip`.
   - `release` — создание релиза на GitHub и прикрепление архивов.

## 6. Поиск опубликованного релиза и скачивание сборок

После успешного завершения всех этапов GitHub Actions:
1. Перейдите на вкладку **Releases** на главной странице репозитория GitHub.
2. Найдите созданный релиз с именем тега (например, `v0.2.0`).
3. В разделе **Assets** скачайте необходимые архивы:
   - `WirePack-linux-x64.zip` (для Linux x64)
   - `WirePack-win-x64.zip` (для Windows x64)

## 7. Действия при ошибке сборки

Если в процессе выполнения GitHub Actions произошла ошибка (на этапе тестов или сборки):
1. Откройте детали упавшего workflow в разделе **Actions**, чтобы изучить лог ошибки.
2. Исправьте проблему локально в коде, зафиксируйте изменения (`git commit`) и отправьте в `main` (`git push origin main`).
3. Если тег был отправлен преждевременно или сборка провалилась из-за дефекта в теге, удалите ошибочный тег (см. раздел 8), исправьте ошибку и создайте тег повторно.

## 8. Особенности исправления ошибочно созданного тега

Если тег был создан по ошибке (например, неверный номер версии или сбой сборки), выполните следующие шаги для его удаления:

1. **Удаление локального тега:**
   ```bash
   git tag -d v0.2.0
   ```
2. **Удаление тега с удаленного сервера (GitHub):**
   ```bash
   git push origin --delete v0.2.0
   ```
3. **Удаление созданного GitHub Release (если он успел сформироваться):**
   - Перейдите в раздел **Releases** на GitHub.
   - Откройте ошибочный релиз, нажмите **Delete release**.
4. После исправления причин ошибки в коде создайте и отправьте корректный тег заново.
